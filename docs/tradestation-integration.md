# TradeStation integration

Facts come from the TradeStation v3 docs and OpenAPI spec (https://api.tradestation.com/docs/specification/), checked on 2026-10-20 and against SIM on 2026-10-22 and 2026-10-26 (regular session; options and orders exercised, samples in `engine/test/fixtures/sim/`). Items marked **(verify)** are not confirmed by the docs or by the SIM spike. The approval notice is in [`references/TRADESTATION_API_APPROVAL.md`](../references/TRADESTATION_API_APPROVAL.md).

All TradeStation calls are made by the client's `ClientCoordinator` DO ([architecture.md](architecture.md)). Nothing else holds tokens.

## Credentials and OAuth

- Each client brings **their own** API key (`client_id`) and secret. They are stored encrypted in `broker_connection`. The key is an Auth0 key: authorize and get tokens only through the v3 auth endpoints.
- Flow: Authorization Code with the client secret (PKCE is a separate key mode for SPAs/native apps; we don't need it).
  - Authorize: `https://signin.tradestation.com/authorize?response_type=code&client_id=…&audience=https://api.tradestation.com&redirect_uri=…&scope=openid offline_access MarketData ReadAccount Trade OptionSpreads&state=…`
  - Token: `POST https://signin.tradestation.com/oauth/token` (code exchange and `refresh_token` grant).
  - Revoke: `POST https://signin.tradestation.com/oauth/revoke`. It revokes **all** refresh tokens of that API key.
- Callback URLs must use `https://` and be registered on the client's key; localhost on ports 80/3000/3001/8080/31022 is allowed by default. Registering ours is optional (D35): by default the app authorizes with the bare `http://localhost:3000` (see the connect flow below). Production callback, for registered mode only (`CONNECT_REDIRECT_MODE`, where the screen tells the client which URL to register): `https://thereelcapital.com/conexion/callback`.
- `OptionSpreads` is the scope TradeStation's [scopes page](https://api.tradestation.com/docs/fundamentals/authentication/scopes) lists for "options related endpoints". Without it every options endpoint (expirations, strikes, chain) answered 403 `{"Message":"Missing required scope."}` in the SIM spike (`engine/test/fixtures/sim/expirations/expirations.json`). Requesting it fixed that: the options endpoints answered 200 on 2026-10-26. A connection authorized before this scope was added lacks it, and the access tokens the engine refreshes keep the scopes of the original authorization, so that client must press «Reconectar con TradeStation» once. The transport maps that 403 to `Rejected` with the code `MISSING_SCOPE`, and the chain reads answer `RECONNECT_REQUIRED` with Spanish copy that tells the client to reconnect.
- `state` binds the callback to the logged-in REEL CAPITAL session. The callback only links the authorization to that existing profile.

### Connect flow (implemented)

1. `/conexion` (fresh session) posts `client_id` and secret. The web Worker passes them straight to the client's DO (`beginConnection`) and never stores or echoes them. The DO encrypts the secret (AES-GCM, `CREDENTIALS_KEY`, [auth-and-security.md#secrets](auth-and-security.md#secrets)), keeps it in `oauth_attempts` with a random 256-bit `state` (hex), single use, expiring after 10 minutes, and returns the authorize URL. A new attempt replaces the previous one.
2. **Paste mode (default, D35; `CONNECT_REDIRECT_MODE` in `src/lib/domain/config.ts`).** `redirect_uri` is `http://localhost:3000` (`connectRedirectUri`, the one source for the authorize URL and the code exchange). The `connect` action returns the authorize URL instead of redirecting; the page opens it in a new tab and shows the steps: log in, allow, the next page will not load (expected), copy its whole address and paste it. The `paste` action parses it (`parsePastedRedirect`, `src/lib/domain/connect-redirect.ts`): origin exactly `http://localhost:3000`, path `/`, no credentials or fragment, only `code`, `state`, `error` and `error_description`, each once. An `error` is `AUTHORIZATION_DENIED`, anything else foreign is `PASTE_INVALID`, a missing state is `STATE_INVALID`. The pasted value is never echoed, stored, logged or audited; only the outcome is. Then the engine checks the state as below. **Registered mode:** TradeStation redirects the browser to `/conexion/callback?code=…&state=…` (a key that registered it).
3. In both modes the engine checks the state. The state is only valid in the DO of the session user, so a foreign, missing, expired or reused state is rejected (`STATE_INVALID`) before anything is sent to TradeStation. The state is consumed before the token request, so a replay finds nothing even if the exchange fails.
4. The DO exchanges the code at `/oauth/token` (form-encoded `grant_type=authorization_code`, `client_id`, `client_secret`, `code`, `redirect_uri`), lists the accounts with the access token against the SIM base, and only then writes `broker_connection` (D1: encrypted secret, encrypted refresh token, `key_id`, `status = CONNECTED`, `refresh_expires_at` = NULL (unknown), see [Token lifetime](#token-lifetime)). The access token is kept in the DO's memory only and renewed by the refresher ([Token lifetime](#token-lifetime)). If the account listing fails, the grant is revoked (unless another connection uses the same `client_id`, D49) and nothing new is stored; revoking kills every grant of that API key, so a stored connection with the same `client_id` is deleted (with its cached accounts) and one with another key is kept. When the key differs from the stored one, the previous key's grant is revoked (best effort) before the row is replaced.
5. Accounts shown: `AccountType` Cash or Margin with `Status` Active (matched case-insensitively), cached in the DO (`broker_accounts`) as of connect time.
6. Disconnect (fresh session) calls `/oauth/revoke`, then deletes the stored credentials whether or not the revoke succeeded, and tells the client if it did not. Revoking removes **every** refresh token of that API key, so Disconnect (and replacing a client's key with another) skips the revocation while another connection uses the same `client_id` (D49): it deletes the credentials, answers `sharedKey: true`, and the screen says why it did not revoke.

Failures carry stable codes (`STATE_INVALID`, `TOKEN_EXCHANGE_FAILED`, `BROKER_UNAVAILABLE`, `INVALID_BROKER_RESPONSE`) mapped to Spanish copy; response bodies from the auth endpoints are never logged because they can echo submitted values. Nothing here is retried.

Exercised against SIM with a real key in the spikes of 2026-10-22 and 2026-10-26 (#21). Observed on SIM (2026-10-22, `engine/test/fixtures/sim/`): the SIM host lists two accounts, `AccountType` Margin and Futures, both `Status` `Active` (`accounts/accounts.json`); the Margin one carries `AccountDetail`. The code exchange granted `openid MarketData ReadAccount Trade OptionSpreads offline_access` (`auth/code-exchange.json`, 2026-10-26, so the options endpoints work). Still **(verify)**: the revoke body field (`token` in the official example, `refresh_token` in its parameter table, so both are sent), and whether the `Status` strings other than `Active` match the ones we filter on.

## Token lifetime

- Access token: 20 min (`expires_in: 1200`). It lives in the DO's memory only. `TokenRefresher` (`engine/src/refresh.ts`) renews it when less than 5 minutes remain, from a DO alarm armed after connecting and after every refresh, and on demand when a caller asks for a token. One refresher per client; concurrent callers share the request in flight (single flight).
- Refresh grant: `POST /oauth/token`, form-encoded `grant_type=refresh_token`, `client_id`, `client_secret`, `refresh_token`.
- Refresh token: by default **non-expiring and non-rotating**. If the key is configured for rotation, each refresh returns a new refresh token, and rotating tokens have a **24-hour absolute lifetime**. The 24 h applies only to keys that rotate (D44): a key that never returns a new token is never marked `expired`, and the refused refresh below is its safety net (the official page also says they expire and rotate every 30 minutes), which matches the approval notice for professional data subscribers.
- Rotation is detected by a new `refresh_token` in the response. The new token, the status and `refresh_expires_at` (unchanged: the lifetime is absolute; NULL when the client connects, because a non-rotating key has no countdown, and set to now + 24 h on the first rotation for a row that has none, D44) are written in one D1 `UPDATE` guarded by the old ciphertext, so a reconnect during the request wins. The new token (the only valid one) is first stored encrypted in the Durable Object's own storage (`unsaved_refresh_token`, keyed to the D1 ciphertext it replaces) and removed once D1 accepts it. If the D1 write fails, the next refresh sends that token and writes it, whatever that response says, and it is recovered the same way after the object is evicted. A reconnect or disconnect discards it. A response without a new token leaves the stored one untouched. A non-rotating key therefore has no countdown (`refresh_expires_at` stays NULL); a rotating key's 24 h start at its first rotation, and a refused refresh is the hard stop for both. Migration 0008 cleared the connect-time values stored before D44 and returned the rows it had marked `expired` to `connected`.
- Only the refresh grant is retried (`Effect.retry`, 2 retries) and only when TradeStation is unreachable or answers 5xx/429. A 4xx refusal is **not** final at once (D49): it is retried with a doubling wait (`REFRESH_RETRY_DELAY_MS` x 2^(n-1): 1, 2, 4, 8 min) and the connection becomes `revoked` only at the `REFRESH_REJECTIONS_BEFORE_REVOKED`-th refusal in a row (5, undecided: `docs/open-questions.md`). The count and the next allowed attempt live in DO storage, so callers asking for a token inside the wait do not reach TradeStation; a success or a reconnect clears them. `broker.refresh_failed` carries `code` (the standard OAuth `error` value, `invalid_grant`, `invalid_client`..., or `other`; never the body, a description or a token), `status` and `rejections`. Why a shared key is refused: the official Refresh Tokens page says a revocation request revokes ALL refresh tokens of the API key, and that rotating keys issue a new token at every refresh (30 min expiry, 24 h absolute); it does **not** say whether a new authorization or a refresh for the same key invalidates tokens issued earlier to another login, so that is (verify). If TradeStation did invalidate them, no retry helps: the only recovery is the client pressing «Reconectar con TradeStation» (an app-wide «not connected» alert is separate work). Not diagnosed: the 2026-10-27 production revocations of two clients; the `broker.refresh_failed` events of that day were not readable from here (unverified).
- Status, as `ConnectionHealth` in `src/lib/domain/connection.ts`: `ok`, `expiring` (known expiry within 2 h), `expired` (the known absolute expiry passed; no refresh is tried), `revoked` (refresh refused several times in a row; `error` while it is being retried), `error` (unreachable or undecodable; retried by the alarm every minute). The `connection` RPC returns it with `entriesBlocked`. `expired` and `revoked` are final until the client reconnects; no further refresh is tried.
- A refresh that finishes after the client reconnected or disconnected is dropped. A key that cannot decrypt the credentials counts as a failed refresh. On any failed refresh: entries are blocked, every open position's `protection_state` becomes `unverified`, a `broker.refresh_failed` event is written, and `reconciliation_pending` is set. Connecting and disconnecting set `reconciliation_pending` and mark open positions `unverified` too (`holdForReconciliation`, atomic with the account cache), so a first connect also starts blocked. Reconnecting restores the connection but **not** the entries: only `markReconciled` (called by the sync loop, M4, after it re-reads orders and positions on a usable connection) lifts the block. Exits and cancels are never blocked by this ([order-lifecycle.md](order-lifecycle.md)). The UI shows the state in the top bar with «Reconectar con TradeStation».
- **Observed on SIM** (spike of 2026-10-22): the refresh grant answers 200 with `expires_in: 1200` (a 20 minute access token) and **no** `refresh_token`, so this key does not rotate (`refresh/refresh-grant.json`). A refused refresh answers **403** `{"error":"invalid_grant","error_description":"Unknown or invalid refresh token."}` (`refresh/refresh-refused.json`); the engine counts any 4xx other than 429 as a refusal (retried, then final), which covers it (`engine/test/refresh.test.ts`, "recorded SIM answers"). Still **(verify)**: the error at the absolute expiry of a rotating key's refresh token (not observable in one session). Decided (D44): the 24 h counts from the first observed rotation and a key that does not rotate has no expiry.

## Environments

**SIM only. No real money, ever.** The only base URL in code is `https://sim-api.tradestation.com/v3`. LIVE is not a configured environment: there is no live URL constant, setting or code path, and the pre-commit hook and the `guards` CI job reject any added line naming the live host outside `docs/` (with or without a scheme, port or version path). The allowlist in `.githooks/no-live-host` is explicit: the OAuth `audience` value (a required identifier of the token request, not a request target) in `engine/src/tradestation/endpoints.ts` and the tests, and documentation links in Markdown. It is tested by `scripts/no-live-host.test.ts`. Adding LIVE would require an explicit decision by the owner and is out of scope.

The DO rejects any mode other than SIM before making a call. SIM accounts are identified by the host that lists them: `GET /brokerage/accounts` on the SIM base returned the Margin and Futures accounts above (`accounts/accounts.json`); no other marker is relied on. Whether one token serves both SIM and LIVE stays unknown, because testing it would mean contacting the live host, which is forbidden. SIM fills are instantaneous with fake money, so SIM proves integration, not execution quality.

## Adapter (`engine/src/tradestation/`)

The TradeStation implementation of the `BrokerAdapter` interface ([architecture.md](architecture.md)). Its HTTP layer is `http.ts`:

- **SIM guard.** `makeTransport` refuses any mode but `SIM` (`MODE_NOT_SIM`) and any base URL that is not exactly the SIM base (`BASE_URL_NOT_SIM`), so a LIVE configuration fails at construction, before a token is requested. Every request is re-checked against the SIM base right before `fetch`.
- **Errors.** 401 → `AuthExpired`; 429 → `RateLimited` (`retryAfterMs` from `X-RateLimit-Reset`, which the docs define as seconds until the limit resets; there is no `Retry-After`); other 4xx → `Rejected` (`code` = the body's `Error`, else `HTTP_<status>`); 5xx or a dropped connection → `Unknown`; an aborted or timed-out request → `Timeout`. The latest `X-RateLimit-*` headers are kept (`rateLimit()`), also from successful responses, and a `RateLimited` error carries the headers of the 429 (`rateLimit`) besides `retryAfterMs`. The older `endpoints.ts` helper (accounts, auth) refuses any URL whose origin is not exactly the SIM API or the auth tenant, without sending.
- **Retries.** Only `get` (reads) retries, twice, after a `Timeout`, a 5xx or a dropped connection. `send` (orderconfirm, place, cancel) makes exactly one attempt: a `Timeout` or `Unknown` there means the order may exist, and the caller marks the intent UNKNOWN ([order-lifecycle.md](order-lifecycle.md), rule 2).
- Tokens come from `TokenRefresher.accessToken()`; a connection without a usable token fails with `AuthExpired` without sending anything.

- **Reads** (`market.ts`): accounts, symbol details (only `STOCK` and `STOCKOPTION` are in scope; anything else is `Rejected` `OUT_OF_SCOPE`), quotes (at most 100 symbols; a symbol the broker answered with an error is absent), option expirations (ISO dates, unique, ascending), strikes (`spreadType=Single`, micro-dollars) and the chain snapshot. Prices and strikes are converted from decimal strings to integer micro-dollars without floats; more than six decimals is refused (`Unknown`). A quote side the broker did not send is `null` in `Quote` (bid, ask, last, trade time), never 0: a missing or one-sided quote must not pass as a price. Option symbol details return `option` (underlying, expiration date, strike in micro-dollars, right) from `Underlying`, `ExpirationDate`, `StrikePrice` and `OptionType`, which the positions table joins by symbol; the positions endpoint itself carries no contract fields.
- **Chain snapshot.** Strikes (`spreadType=Single`, plain-date `expiration`) are listed first, then both option symbols of every strike are quoted in requests of at most 100 symbols (SIM-verified on 2026-10-26: option quotes are served by the snapshot endpoint). A symbol the broker does not return, or one without both bid and ask, is left out, so the screen shows it as missing, never as 0. A failure of either call is the usual `BrokerError`. The engine lists an expiration's strikes once and passes them to the snapshot, then reuses them for `CHAIN_STRIKES_CACHE_MS` (10 min), so the first read costs one strikes call (options bucket, 90/min) plus `ceil(2 × strikes / 100)` quotes calls (500 per 5 min) and each live refresh (D46) costs the quotes calls only. **(verify)** The symbol is built as `<underlying> <yymmdd><C|P><strike without trailing zeros>`, the shape of every sampled symbol; an unknown symbol is assumed to be omitted or listed in `Errors` rather than failing the whole request; underlyings whose options use another root are not covered.
- **Fixtures** in `engine/test/fixtures/` are derived from the spec's examples, not recorded ([README](../engine/test/fixtures/README.md)); #21 replaces them with recorded SIM samples.
- **Observed on SIM (2026-10-26):** `spreadType=Single` and a plain-date `expiration` (`2026-10-30`) are accepted by strikes (`expirations/strikes-single.json`, 32 strikes) and by the chain stream (`chain/chain-stream.json`); expirations are `{Date: "2026-10-30T00:00:00Z", Type: "Weekly", Root}` (`expirations/expirations.json`). Without `strikeProximity` the chain returned 733 rows for one expiration of `F`. Each row has `Ask`, `Bid`, `Mid`, sizes, `Side`, `Strikes` and one entry in `Legs` (`Symbol`, `StrikePrice`, `Expiration`, `OptionType`, `AssetType` "StockOption"). **The stream sent 733 messages in 30 s and no `EndSnapshot`** (the file keeps 12 of them and the total), so a reader that waits for `EndSnapshot` never finishes on this chain; the chain is therefore built from strikes and quotes instead (#249). No heartbeat was seen in the 30 s window. Option quotes through `/marketdata/quotes` are covered in the table above.
- **(verify)** in the SIM spike: the option symbol shape the chain builds (`<underlying> <yymmdd><C|P><strike>`) for every in-scope underlying; and how `/marketdata/quotes` reports an unknown option symbol (an `Errors` entry is assumed, not a failed request).

- **Orders and positions** (`orders.ts`, `status.ts`): ids are batched by 10 per request. Orders: only single-leg long equity and option orders are represented; spreads and short sales made elsewhere are left out. Positions: shorts are reported with `side: "short"` (unsigned size) so the engine can see them and refuse to trade around them. If the response lists any per-account `Errors`, the call fails (`Rejected`) rather than return a partial picture that reconciliation would read as "flat". Positions' P&L fields are not decoded. **Observed on SIM (2026-10-26):** the orders listing does **not** echo `OrderConfirmID` (order fields: `AccountID`, `CommissionFee`, `ClosedDateTime`, `Currency`, `Duration`, `FilledPrice`, `Legs`, `OrderID`, `OpenedDateTime`, `OrderType`, `PriceUsedForBuyingPower`, `Routing`, `Status`, `StatusDescription`, `UnbundledRouteFee`; `equity-order/orders-listing.json`), so `BrokerOrder.orderConfirmId` (explicitly `string | null`) is always `null` here, and reconciliation of an UNKNOWN place, whose response was lost and so has no `OrderID`, uses the fallback match, which is account, symbol, trade action, quantity and open time (an order opened after the intent was SENT and not already matched to another intent); if exactly one order fits it is adopted, and if several or none fit the intent stays UNKNOWN for a human (implemented in `engine/src/reconcile.ts`; a `REJ` record left by a resent id fits the same match and makes it ambiguous, so the intent then stays UNKNOWN for a human; the open-time allowance and the send grace are in `src/lib/domain/config.ts`). The statuses seen on SIM were `ACK` (a working stop), `FLL`, `REJ` and `OUT` (a cancelled stop, `StatusDescription` "UROut"), all mapped as above; a fill carries `FilledPrice`, and each leg `ExecQuantity`, `QuantityRemaining`, `ExecutionPrice`, `OpenOrClose`, `BuyOrSell`, plus `ExpirationDate`, `Underlying`, `OptionType` and `StrikePrice` for options (`fill-fields/orders-today.json`). A partial fill (`FPR`, `FLP`) could not be forced and stays unobserved. The status table above is implemented exactly; `RJC` and `RJR` also appear in the spec's status enum and may be rejections (**verify**), but stay unmapped until observed.

- **Orders** (`trading.ts`): place sends one MARKET, `DAY`, `Intelligent` order with `OrderConfirmID`, `orderconfirm` sends the same body without the id, and cancel is a `DELETE` with no body; the request type has no field for anything else, and a mismatch between asset type and trade action (`BUY`/`SELL` for equities, `BUYTOOPEN`/`SELLTOCLOSE` for options), a quantity that is not a positive integer or an order id that is not digits is `Rejected` before anything is sent. **`OrderConfirmID` is limited to 22 characters** by the spec (its example is 16 random bytes in base64 without padding), so intent ids must fit: a longer id is refused (`INVALID_ORDER_CONFIRM_ID`), which `prepareEntry` respects by minting 22-character base64url ids. The entry path does not call `orderconfirm`. It treats `Rejected`, `AuthExpired` (401) and `RateLimited` (429) on place as "not placed" and `Timeout`/`Unknown` as UNKNOWN (**verify** in #21 that a 401 or 429 can never leave an order behind). `orderconfirm` omits the id. Observed: it also accepts one (`confirm/orderconfirm-with-id.json`) but answers with its own generated `Confirmations[].OrderConfirmID`, unrelated to ours, so that field is not usable for correlation; a place with the same id right afterwards was accepted and filled (`equity-order/place.json`), so a preview does not reserve the id; omitting it stays the safer choice. A cancel that races a fill answers **400** `{Error: "BadRequest", Message: "Not an open order."}` and the order ends `FLL` (`cancel-race/cancel.json`), which the adapter reports as `Rejected`; the next sync shows the fill. A 200 answer with only `Errors` is `Rejected` (the spec's example); a 200 with neither an `OrderID` nor an error is not understood and is `Unknown`, since the order may exist.
- **SIM account guard.** The docs name no marker that tells a SIM account from a live one (the SIM spike found no marker besides the host that lists them, so the guard does not rely on an `AccountID` pattern). So before any `orderconfirm`, place or cancel, the account must appear in `GET /brokerage/accounts` fetched through the SIM host and be active Cash or Margin; the list is cached and refetched once when an id is missing. The first sync pass after a Durable Object start verifies the client's accounts through the same guard, in parallel with its first read, so the first order does not pay for the listing; if that fails the guard checks again before sending. Otherwise the call is `Rejected` with `ACCOUNT_NOT_SIM` and nothing is sent. Together with the construction check this means an order request needs a SIM base URL, `SIM` mode and a SIM-listed account.
- **Wiring.** `makeTradeStationAdapter(config)` builds the SIM adapter and `tradeStationLayer(config)` provides it as an Effect service (failing with `SimOnlyRefused` when SIM cannot be proven). `engine/src/broker/provider.ts` (`resolveBroker`) is what the Durable Object calls, once per instance: TradeStation SIM in production, and the local simulation only with an explicit `BROKER=local-sim` in `development` or `test` (`broker/select.ts`).

## Protection (engine-held, D36)

Stops and trailing are held by the engine: on each sync tick the DO compares fresh bids with the effective exit level and sends a MARKET sell of `available` through the normal exit path. No `StopMarket` or trailing `StopMarket` order is placed at the broker, so there is never more than one working sell per position. Protection depends on our uptime and the client's token, which is why the DO exposes one `protection_state` the UI shows as is:

- `verified`: the engine has a fresh quote and a valid token and is actively monitoring.
- `unverified`: the quote is stale, the token expired or failing, or the engine cannot monitor.
- `none`: no protection applies (no open position or nothing to protect).

Future work only: v3 supports `StopMarket` and `AdvancedOptions.TrailingStop`, and the spike of 2026-10-26 showed both accepted on a long option in the regular session with `DAY` (`stops/stopmarket.json`, `stops/trailing-stopmarket.json` with `AdvancedOptions.TrailingStop.Percent`). A working stop is `ACK` with `StopPrice` and `AdvancedOptions` (`STPTRG=SAB;`, `TRL=10%;`), and cancelling it answers 200 "Cancel request sent", then the order is `OUT` (`stops/*-cancel.json`, `*-listing.json`). How a triggered stop fills was not observed. GTC orders live at most 90 days. A broker-held stop could be added later if SIM supports it; it would need every scale-out to cancel/replace it.

## Limits and streams

- Rate limits are per key, and each client has their own key. Quotes: 500 requests / 5 min. Accounts/orders/positions: 320 / 5 min per resource on SIM (observed 2026-10-22: `x-ratelimit-limit: 320`, `x-ratelimit-period: 300`, `x-ratelimit-resource: sim-get-accounts`, `rate-limits/probe-*.json`; the quotes resource showed 500 / 300 s, `quotes/quote-equity.json`). The four headers are `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset` (seconds, 1 to 4 in the samples) and `x-ratelimit-period`, plus `x-ratelimit-resource` naming the budget; read them rather than hard-code numbers. The token endpoint's headers carry only limit (500), remaining and a reset that is an epoch value (`refresh/*.json`). Re-observed 2026-10-26 on accounts: limit 320, remaining 318, reset 3, period 300, resource `sim-get-accounts`. The refresh grant on 2026-10-26 again returned `expires_in` 1200 and no new `refresh_token`; the absolute 24 h expiry is not observable in one session. Options endpoints: 90 / min. HTTP 429 when exceeded.
- **Live screen prices (D47, polling of D46 as fallback).** The coordinator holds one `GET /marketdata/stream/quotes/{symbols}` per 100 symbols of the union, up to 5 per client (SIM base URL only, through the same transport guard as every call; never retried inside a run) with the union of the symbols its open screens watch, and pushes updates to the pages over WebSockets (`engine/src/quote-hub.ts`, `engine/src/live-sockets.ts`, `engine/src/tradestation/quote-stream.ts`). A union of more than 100 symbols (`LIVE_STREAM_MAX_SYMBOLS`) is spread over several streams, at most `LIVE_STREAM_MAX_STREAMS` (5, so 500 symbols) per client; a symbol stays on its stream while any screen watches it and new symbols fill the streams with room, so a change restarts only the stream whose symbols changed. A stream whose symbols change is replaced make-before-break (#276): the run for the new set is opened beside the old one, the old one keeps delivering until the new one does and is then aborted, so a symbol that stays watched has no gap in ticks, and a stream has at most two runs open for that moment (if the new run fails before delivering, both are closed and the stream backs off); a stream that has not delivered yet is restarted at once. A break restarts a stream after 1, 2, 4 … 30 s (per stream), and none is left open when no socket is. The screens are told `unavailable` while any stream is down and `live` again once every stream is up (a screen that joins is told the current state at once), and a page that heard `unavailable` polls until it hears `live`, whatever quotes the healthy streams deliver meanwhile. A persisting stream failure is logged once per kind, not once per stream. The reader cuts the chunked body into top-level JSON objects (chunk boundaries are not message boundaries), merges a message that leaves a side out with the previous value of that symbol, and treats a blank side as no market, never 0. `StreamStatus: GoAway` ends the run (restart); `Error: DualLogon` fails it with the code and the hub reconnects after the backoff; any other `Error` is taken as one symbol's (an unknown or expired contract) and skipped, so one bad symbol does not end the stream for every screen **(verify)**; a stream that delivers nothing, not even a heartbeat, for `LIVE_STREAM_IDLE_MS` (30 s) is treated as broken and restarted (the transport timeout covers only the connect); every tick is forwarded to the pages at once, including the entry symbol's, and the entry is then sized again from the streamed ask without a D1 read: SIZE and the connection row are held in the coordinator (`engine/src/entry-inputs.ts`) and dropped by the admin saving a client's settings (`settingsChanged`), by any change of the stored connection (token refresh, connect, disconnect) and after `LIVE_ENTRY_INPUTS_TTL_MS` (60 s) as a backstop; the limits are read from the coordinator's own storage on every tick, and ticks that arrive while a sizing runs collapse into the latest (there is no fixed gap any more), and after a failed sizing (details read failed, symbol rejected) ticks of that symbol are not sized again for `LIVE_ENTRY_RETRY_MS` (5 s), so a failure costs one broker call and one event row per interval, not per tick; `Heartbeat` is forwarded to the pages as «alive» so a quiet symbol does not read as stale. **(verify)** all of these against SIM, none was run when this was written: the exact quote message fields (full quote or only the changed ones: the merge covers both), the heartbeat shape and interval (the HTTP streaming page says every 5 s idle; the spec page of the quote stream could not be read), the stream's symbol limit (we cap a stream at 100, the snapshot's limit), how many streams one key may hold at once, counting the second run a handover opens for an instant (we open one for up to 100 symbols and up to 5 for a long option chain; the first rejection on SIM sets the real cap), what a second logon with the same key does (`DualLogon`), and whether SIM delivers quotes outside the regular session. Polling the quotes snapshot (below) takes over on a page whenever the socket is down, silent for 8 s, or the engine says `unavailable` (always, for the local simulation, which has no stream).
- **Polling fallback (D46).** Nueva entrada polls the quotes snapshot through the engine's `prepareEntry` (one quotes call per poll, 2 s apart per open screen, 150 of the 500 requests / 5 min; the symbol details are cached). On a quotes failure the screen slows down (2, 4, 8, 16 s) instead of retrying at the base pace. **(verify)** how SIM answers a 429 on the quotes resource.
- Streams: chunked JSON where chunk boundaries are not message boundaries; `Heartbeat` every 5 s idle (verify); `StreamStatus: EndSnapshot | GoAway` (v3 order and position streams document them; the quote stream is assumed to behave alike, verify); `Error: DualLogon` means close, wait and reconnect.

## Reading the latency events

The `ClientCoordinator` prints one JSON line per measurement so the distance between the Durable Object, TradeStation and D1 can be read in production (#279). Run `wrangler tail reel-engine --format json` and filter on the event name inside each log line (`jq 'select(.logs[]?.message[]? | tostring | contains("broker.request"))'`, or just `grep`).

| Event | Fields | Meaning |
| --- | --- | --- |
| `broker.request` | `operation`, `status`, `ms` | One TradeStation request. `operation` is the adapter's operation (`accounts`, `quotes`, `quoteStream`, `optionStrikes`, `chainSnapshot`, `placeOrder`, `orders`, ...) or `auth` for the token endpoints. `status` is the HTTP status, or `null` when no response arrived (timeout, network). `ms` is the time until the response headers; for `quoteStream` that is the time to first byte, once per stream start. |
| `d1.query` | `name`, `ms` | One D1 read from the Durable Object: `connection_row`, `size_usd`, `protection_settings`, `token_row`. |
| `do.colo` | `colo` | The Cloudflare data center this Durable Object instance runs in, once per instance (from `cloudflare.com/cdn-cgi/trace`, the `colo` line only). |

The lines never carry URLs, query strings, symbols, account ids, tokens or bodies.
