# Authentication and security

Library: **Better Auth** (`better-auth` + `@better-auth/passkey`, 1.7.x on 2026-10-20). Plugins: `admin`, `passkey`, `sveltekitCookies` (last).

**The app sends no email** (owner decision, 2026-10-21). The admin creates each client and hands over a single-use activation link personally; the client's email is only an identifier and is never verified. There is no email provider, no email OTP and no password.

## Gaps in Better Auth defaults

Better Auth's defaults do **not** meet our requirements in three places. Each needs app code and a test:

| Requirement | Better Auth default | What we do |
| --- | --- | --- |
| Passkey with user verification | registration UV can be requested, but verification is hard-coded `requireUserVerification: false`; sign-in sends `userVerification: "preferred"` | set `authenticatorSelection.userVerification: "required"` and throw in `registration.afterVerification` / `authentication.afterVerification` when `userVerified` is false |
| First passkey without email or password | passkey registration needs an existing session, and nothing else signs a new user in | after validating an activation link, the app creates a short-lived **enrollment session** that can only register a passkey; every other route rejects it |
| Single-use recovery codes | 2FA backup codes need TOTP/OTP 2FA enabled and are encrypted, not hashed | app-owned `recovery_codes` table (see below) |

## Configuration

- `emailAndPassword: { enabled: false }`; users are created only by an admin through `auth.api.createUser` (no password).
- `passkey({ rpID: "thereelcapital.com", origin: "https://thereelcapital.com", authenticatorSelection: { residentKey: "required", userVerification: "required" } })` plus the UV checks above.
- `admin({ adminRoles: ["admin"] })` is installed for the `createUser` call, the `role`/`banned` columns and the banned-sign-in block. Its HTTP endpoints are not usable (see [Endpoint allowlist](#endpoint-allowlist)); `/admin/impersonate-user` and `/admin/set-user-password` stay in `disabledPaths` as well.
- `rateLimit: { enabled: true, storage: "database" }` (in-memory limits are per isolate on Workers) and `advanced.ipAddress.ipAddressHeaders: ["cf-connecting-ip"]`.
- `session.freshAge`: Better Auth measures it from session creation, and its `sensitiveSessionMiddleware` does **not** check freshness. For sensitive app actions we check `now − session.createdAt < 10 min` ourselves; re-auth = a new passkey sign-in.
- Secret in `BETTER_AUTH_SECRET` (Workers Secret, declared under `secrets.required` in `wrangler.jsonc`). Schema via `bunx auth@latest generate --config scripts/auth-schema.ts` → D1 migration (`migrations/0002_better_auth.sql`).
- Code: `src/lib/server/auth.ts` builds the instance, and `src/lib/server/shared-auth.ts` keeps one per isolate (rebuilt only if the D1 binding, secret or origin change; building it runs Better Auth's schema check, a dozen D1 statements, which used to run on every request; Better Auth keeps per-request state on a per-call copy of its context, so sharing is safe; the session cookie cache is on for reads only ([Session cookie cache](#session-cookie-cache), D43)); `src/hooks.server.ts` adds `sveltekitCookies` last, exposes the instance as `locals.auth` (the admin create-client action uses it instead of building another), resolves the session into `locals.session` / `locals.user` and mounts `svelteKitHandler`. `baseURL`, the passkey `rpID` and the passkey `origin` all derive from one public variable, `APP_ORIGIN` (`https://thereelcapital.com` in `wrangler.jsonc`; local runs override it in `.dev.vars` or with `--var`), never from the request. The web Worker sets `workers_dev: false`: passkeys are bound to the domain, so no other hostname may serve the app.
- Passkey user verification is requested (`userVerification: "required"`) and enforced in `registration.afterVerification` and `authentication.afterVerification` (`requireUserVerified` in `src/lib/server/passkey-policy.ts`): an unverified ceremony fails with 403 `USER_VERIFICATION_REQUIRED` before any passkey is stored or session created. A banned user's sign-in fails with 403 `BANNED_USER` (the admin plugin refuses to create the session) and a Spanish message.
- Recovery endpoints are a Better Auth plugin (`src/lib/server/recovery-plugin.ts`) so they get its rate limiter (`RECOVERY_REDEEM_RATE_LIMIT`: 5 attempts per 10 minutes per IP, D28, in `config.ts`) and cookie handling. `POST /api/auth/recovery/redeem {code}`: one answer, 401 `INVALID_RECOVERY_CODE`, for a wrong, used or suspended-account code; redeeming runs one D1 batch (`redeemRecoveryCode`): spend the code (the atomic `UPDATE`), then, only if this call spent it, write the `recovery.redeem` audit row and a `recovery.passkeys_delete` row (the number of passkeys deleted, never their material), delete **all** of the client's passkeys and delete every session, so there is no window in which the old passkey still works and a failure leaves everything intact (D27). The client's other unused codes stay valid, so a recovery interrupted before a new passkey is registered is retried with another code. Then the enrollment session is created (and any session a racing redemption created is removed); if that fails, the code is released again (only by the redemption that spent it) so a failed request never costs the client a code. `POST /api/auth/enrollment/complete`: needs an enrollment session in which a passkey was registered (403 `PASSKEY_REQUIRED` otherwise); it claims the session with a `DELETE` that must change one row, starts a full session, writes a new set of 10 codes (`recovery_codes.issue` audited, earlier codes deleted; the session comes first so a failure never destroys the old set) and returns the codes once with `Cache-Control: no-store`.
- Regeneration: `POST /api/recovery-codes` (`src/routes/api/recovery-codes/+server.ts`, logic in `recovery-regenerate.ts`) calls `requireFreshSession`, replaces the session user's whole set and returns the 10 new codes once (`no-store`), with a `recovery_codes.regenerate` audit row written in the same batch. Only the settings screen (a later milestone) and the shell's recovery-code prompt (a client with no unused codes) call it; the user is always the session user, never a request value.
- Enrollment-only session: a normal Better Auth session with `session.enrollment = true` (migration `0004_enrollment_session.sql`), valid 15 minutes from `createdAt` (Better Auth refreshes `expiresAt` on read, so the age is checked from `createdAt`). `src/hooks.server.ts` runs `enrollmentGate` (`src/lib/server/enrollment.ts`) on every request: such a session resolves as signed out (`locals.user` and `locals.session` are null, `locals.enrollment` is set) and only the listed paths run (the recovery page, passkey registration and sign-in, finishing enrollment, session read and sign-out). Every other path, including every other Better Auth endpoint, answers 403 `ENROLLMENT_ONLY` (pages redirect to `/recuperacion`); an expired one gets 401 `ENROLLMENT_EXPIRED`. Activation links reuse the same mechanism, with `session.invitationId` (migration `0006_session_invitation.sql`) recording the link the session came from; the activation page `/activar/<token>` and `POST /api/auth/activation/redeem` are open to it as well.
- Activation links (`src/lib/server/activation.ts`, `activation-link.ts`, `activation-plugin.ts`). `POST /api/auth/activation/redeem {token}` (a Better Auth plugin endpoint for its rate limit, `ACTIVATION_REDEEM_RATE_LIMIT`: 5 per 10 minutes per IP, D28) looks the token's SHA-256 up, requires the link unused, unexpired, not revoked and its client not suspended, writes an `activation.redeem` audit row and starts the enrollment session (the client's other sessions are deleted by a statement that also checks the link is still open, and the new session is removed if it closed meanwhile, so a request delayed past the client's own activation can neither sign them out nor leave a session on a spent link); every failure answers 401 `INVALID_ACTIVATION_LINK` with one Spanish message, so nothing says which condition failed. Opening the link does not spend it. The first passkey does: `registration.afterVerification` runs `claimInvitation` before the passkey is stored, one `UPDATE ... WHERE used_at IS NULL AND revoked_at IS NULL AND expires_at > now AND <not banned> RETURNING`, so concurrent registrations, a registration racing a regeneration and an expired link all lose; the batch that follows deletes the link's other enrollment sessions and writes `activation.complete`. A failed batch gives the link back. If the passkey row itself then fails to insert (a database error after the claim), the link stays spent and the admin generates a new one; the registration cannot be retried on a spent link. Finishing is the shared `POST /api/auth/enrollment/complete`; the page then goes to `/conexion` (a guarded placeholder until #17). The page `/activar/[token]` (`AccessShell` + `EnrollmentSteps`, shared with `/recuperacion`) has one explicit step, «Comenzar», that posts the token: a link preview or prefetch never opens a session. It sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store, no-transform` (the edge does not inject the Web Analytics beacon into `no-transform` responses, so the token-bearing URL is not reported) and never returns the token from `load`. A reload resumes the passkey step only when the session came from the link in the URL, and after a reload the page asks the server to finish before registering anything, so a passkey that was already saved is never registered twice. A registration refused because the link stopped being valid after it was opened shows the invalid-link message, not the expired-session one.
- `createClient(deps, actor, email)` is a server function (the admin screen calls it through `createClientFromForm` in `admin-clients.ts`, after `requireAdmin` and `requireFreshSession`): `auth.api.createUser` without headers (no password, role `user`), then `client_settings` (SIZE, stop and unlock defaults from `config.ts`), the first link and a `client.create` audit row in one batch; if the batch fails the user is deleted again. `regenerateActivationLink` and `revokeActivationLink` revoke the client's unused links and delete the enrollment sessions created from them in one batch with their audit row (the session that already spent its link is kept: that client has a passkey and may finish). No public route creates users and no code path sends email.
- Tokens are hashed in `src/lib/server/token-hash.ts`. Activation links (32 random bytes, so no key is needed, D32) use `hashActivationToken`: plain SHA-256 of `activation-link:<token>`, so the CLI scripts need no secret. Recovery codes and audit IPs use `hashToken`: HMAC-SHA-256 keyed with `BETTER_AUTH_SECRET`, domain-separated by purpose (`recovery-code:`, `audit-ip:`). Rotating `BETTER_AUTH_SECRET` therefore invalidates every pending recovery code but not activation links.

## Endpoint allowlist

Only the paths in `allowedAuthPaths` (`src/lib/server/endpoint-policy.ts`) answer under `/api/auth/*`; `onRequest` of the `endpoint-policy` plugin returns 404 for everything else, whether Better Auth's core, the admin plugin or an endpoint a future release adds. Better Auth's admin API (`/admin/set-role`, `ban-user`, `create-user`, `remove-user`, `revoke-user-sessions`, ...) answers any admin session with no fresh-session check and no audit row, so the app uses it only in-process (`auth.api.createUser`, which does not pass through the router) and every admin change goes through the guarded, audited `/admin` actions. Adding an endpoint to the list is a security decision: say in the PR what guards it. The same plugin puts a `before` hook on the passkey endpoints that change what can sign in (`generate-register-options`, `verify-registration`, `update-passkey`, `delete-passkey`): a full session older than 10 minutes gets 401 `REAUTH_REQUIRED` (`isFreshSession`, the rule behind `requireFreshSession`), while an enrollment session keeps registration (it can reach nothing else, see `enrollment.ts`). Sign-in, `list-user-passkeys` and sign-out need no fresh session. Covered by `tests/e2e/auth-lockdown.spec.ts`.

## Audit of authentication

Besides the admin mutations, these write `audit_log` rows (`src/lib/server/auth-audit.ts`, the recovery and activation plugins); none stores a code, token, email or other secret:

- `auth.sign_in` (after a passkey ceremony created a session, `{method: "passkey"}`) and `auth.sign_out` (before the session ends), with the user as actor and target.
- `recovery.redeem_failed` and `activation.redeem_failed` for a rejected code or link: actor `anonymous`, no target, `{reason, ipHash}` where `ipHash` is 16 hex characters of the HMAC of the `cf-connecting-ip` value (`hashToken("audit-ip", ...)`). The rate limit (5 per 10 minutes per IP) bounds how many such rows one source can write.
- `activation.redeem` is written only after the enrollment session exists, so a row means a session started; a link that closed in between writes `activation.redeem_failed` with reason `link_closed`.
- `admin.create` from `bun run admin:create` and `admin.recover` from `bun run admin:recover` (actors `cli:admin-create` and `cli:admin-recover`; `admin.recover` stores counts only).

A failed audit write fails the request (the audit helper throws), and for the two that start a session (`auth.sign_in`, `activation.redeem`) `auditStartedSession` first deletes the session just created, because the error response may not carry its cookie; so none of these actions happens unrecorded. Covered by `tests/e2e/auth-audit.spec.ts` and `bootstrap-admin.test.ts`.

## Flows

**First admin:** `bun run admin:create <email>` (local D1) or `bun run admin:create <email> --remote` (production D1); neither needs `BETTER_AUTH_SECRET`; it inserts the admin user, an activation link and an `admin.create` audit row (actor `cli:admin-create`, `src/lib/server/bootstrap-admin.ts`), in one D1 batch, and prints the link once. Opening the link is the activation flow below.

**Last admin recovery:** `bun run admin:recover <email> [--remote]` (D31, `scripts/admin-recover.ts`, `src/lib/server/recover-admin.ts`), run from the owner's machine with `wrangler` logged in, needs no secret. It refuses an unknown email, a non-admin (clients are recovered in the admin panel) and a disabled admin. One D1 batch writes the `admin.recover` audit row (counts of passkeys, unused codes and sessions before), revokes open links, deletes the admin's passkeys, sessions and recovery codes and inserts a new link, printed once. Every statement resolves the target by email and role `admin`, and the email and hash are validated before they are placed in SQL literals.

**Onboarding:**
1. The admin creates the user and `client_settings`. The app generates an activation link `https://thereelcapital.com/activar/<token>` (32 random bytes, base64url), stores only its SHA-256, sets it to expire after 72 hours, and **shows it to the admin once**.
2. The admin shares the link personally (in person or a private message). The app never sends it.
3. The client opens it. The server checks that the token is unexpired and unused (rate-limited, never logged) and creates an enrollment session valid for 15 minutes, tied to that link. Opening the same link again replaces the earlier enrollment session.
4. The client registers a passkey (UV). Registration rechecks that the link is still unused, unexpired and not revoked, then marks it used in the same step.
5. The client receives 10 recovery codes, shown once, then configures TradeStation ([tradestation-integration.md](tradestation-integration.md)).

Trading requires all steps. Using, regenerating or revoking a link ends every enrollment session created from it, so an older session can't register a passkey afterwards. A TradeStation login never creates or activates a profile.

**Sign-in:** passkey only.

**Recovery (self-service):** recovery code → atomic `UPDATE recovery_codes SET used_at = ? WHERE code_hash = ? AND used_at IS NULL AND <user not banned> RETURNING user_id` (rate-limited; the owner comes from the matching hash, so the client types only the code) → in the same batch, revoke all sessions and delete all the client's passkeys (a lost or stolen passkey stops working at once) → short-lived enrollment session that can only register a new passkey → new codes.

**Recovery (admin-controlled):** the admin verifies identity outside the app, then revokes sessions, deletes passkeys and codes, and generates a new activation link to share personally. It requires a fresh admin session, is audited, and never logs the admin in as the client. Implemented in `src/lib/server/admin-client-access.ts` (`recoverClient`): one D1 batch writes the `client.recover` audit row (counts of passkeys, unused codes and sessions before, never their material), closes the open link, deletes passkeys, sessions and codes and inserts the new link, so a failure leaves everything intact. The same recovery works on **another admin** (D31): `recoverAdmin` in the same module, page `/admin/administradores/[id]`, audit action `admin.recover` with the acting admin as actor. It needs a fresh session, refuses the actor's own account (`OWN_ACCOUNT`) and a disabled admin, and only resolves targets with role `admin` (client actions still treat an admin id as not found). Deactivation (`deactivateClient`) sets the same `banned` flag as Better Auth's `banUser` but in one batch with the session deletion and the audit row, which `banUser` cannot do; the sign-in block remains the admin plugin's. The client page's actions never reach the engine, so broker orders are untouched.

A set is 10 codes (`RECOVERY_CODE_COUNT`), each 25 symbols from a 31-symbol alphabet without ambiguous characters (about 124 bits, `ABCDE-FGHJK-…`), drawn with WebCrypto and hashed with `hashToken("recovery-code", …)` over the normalized form (`src/lib/server/recovery-codes.ts`). Codes have no expiry of their own: they stay valid until used or replaced. Issuing a new set deletes every earlier code.

Recovery codes are stored as HMAC-SHA-256 with a server key; activation tokens (256 bits) as a plain domain-separated SHA-256 (D32).

## Sessions and requests

- Better Auth cookie session (Secure, HttpOnly, SameSite=Lax). SvelteKit's origin check plus Better Auth's `trustedOrigins` handle CSRF.
- Every server route and action resolves the user from the session and checks the role. Client-supplied user ids are ignored.
- Server helpers (`src/lib/server/`) make this uniform; routes and actions use them instead of reading `locals` directly:
  - `requireUser(event)` → 401 `AUTH_REQUIRED` without a session, 403 `FORBIDDEN` for a banned user. `requireAdmin(event)` → 403 `FORBIDDEN` unless `role` is `admin`.
  - `requireFreshSession(event)` → 401 `REAUTH_REQUIRED` unless `now − session.createdAt` is under 10 minutes (and not in the future). Admin mutations call `requireAdmin` then `requireFreshSession`.
  - `decode(schema, input)` → Effect `Schema` decode that rejects unknown fields; failure is 400 `INVALID_INPUT` and never echoes input.
  - `audit(db, { actor, action, targetUserId, before, after })` inserts into `audit_log` with bound parameters and throws on a credential-named key at any depth or on a failed write. `auditStatement` returns the statement so a mutation and its audit row commit in one `DB.batch`; use it for every admin mutation.
  - `engineFor(env.ENGINE, event)` → `ENGINE.getByName(session.user.id)`; there is no other way to address a client's Durable Object from web code.
  - Errors carry a stable `code` (`App.Error`) and a Spanish message.
- Guarded layouts: the `(app)` layout load sends anyone without a session to `/acceso` (303) and answers 403 to a banned client (`requireUser`); the `/admin` layout does the same for anonymous visitors and answers 403 to a non-admin. Form actions and `+server` routes still answer 401/403 themselves. The shell makes no call to the engine except through `engineFor` (the connection, read once per navigation (the layout load reruns whenever the URL changes) and handed to `/operar` and `/conexion` through `await parent()`; `shellConnection` copies only the fields the screens render, since layout data is serialized to the browser); the old `ENGINE.getByName("smoke")` ping is gone, so no route addresses a Durable Object by anything but the session user id.
- Disabling a client = `banUser` (it deletes sessions and blocks new ones). It does not touch broker orders. A browser that already holds a cached session copy (below) is served reads for up to 30 s more; its mutations are refused at once.
- Logout or browser close does not affect protections; they live in the DO or at the broker.
- Pages load nothing from other origins except the Cloudflare Web Analytics beacon (`static.cloudflareinsights.com`), injected at the edge in production only (D26 in [decisions.md](decisions.md)).

### Session cookie cache

Decision D43. `session.cookieCache` is on with `maxAge` `SESSION_COOKIE_CACHE_SECONDS` (30 s, `src/lib/domain/config.ts`), so an authenticated read costs no D1 statement instead of two (session and user lookups).

- What it is: a second cookie, `session_data` (same attributes as the session cookie: Secure, HttpOnly, SameSite=Lax, Max-Age 30), holding the session and user fields (including `role`, `banned` and the `enrollment` and `invitationId` session fields) in the default `compact` form: base64url JSON plus an HMAC-SHA-256 signature with `BETTER_AUTH_SECRET`. It is signed, not encrypted: the holder can read their own fields but cannot change them. It is bound to the session token (a cache whose token differs from the session cookie is dropped), expires with its own `expiresAt` and is refreshed from D1 when it runs out.
- Accepted window: a ban, deactivation, role change or session revocation reaches a browser that holds a copy within 30 s, **for reads only**.
- Immediate, by design: `src/lib/server/session-cache.ts` (`mayUseSessionCache`) serves the copy only to GET and HEAD requests outside the auth API and the TradeStation callback, plus `GET /api/auth/get-session`. `hooks.server.ts` reads D1 (`disableCookieCache`) for everything else, and the `session-cache-policy` plugin removes the `session_data` cookie from every other request to the auth API before Better Auth sees it. So every form action, `+server` mutation, admin action, `requireFreshSession` check, passkey user-verification hook, passkey management endpoint, enrollment claim and recovery step runs on D1 state. A banned or revoked session cannot trade, change anything or reach passkey setup, even with a valid copy.
- Sign-out: Better Auth deletes the session row and expires `session_data` with the session cookie in the same response.
- Admin ban, revoke and deactivate (`admin-client-access.ts`) delete the rows in D1; the cached copy on the client's browser lapses by itself.
- Per guard: `requireUser` (banned) and `requireAdmin` (role) accept the copy on reads; on mutations they see D1. `requireFreshSession` reads `createdAt`, which never changes, from a mutating request and therefore from D1. The enrollment gate reads the cached `enrollment` flag on reads and D1 on mutations; the 15 minutes are measured from `createdAt`.

### Security headers

- Content-Security-Policy: `kit.csp` in `vite.config.ts` (SvelteKit adds nonces or hashes to its own inline script, so there is no `unsafe-inline` for scripts). `default-src 'none'`; scripts from `'self'` and `https://static.cloudflareinsights.com`; `connect-src 'self' https://cloudflareinsights.com` (the beacon's reporting endpoint); styles, fonts and images from `'self'` (images also `data:`); `form-action 'self' https://signin.tradestation.com` (the connect form is answered with a redirect to TradeStation's sign-in); `base-uri 'none'`, `object-src 'none'`, `frame-ancestors 'none'`. Style attributes alone are allowed inline (`style-src-attr`): they cannot run script. Passkeys need nothing extra.
- `src/lib/server/security-headers.ts`, applied by the outermost `handle` to every response (pages, endpoints, redirects, the enrollment gate's answers and Better Auth's): `Strict-Transport-Security: max-age=31536000; includeSubDomains` (no `preload`: it is hard to undo and nobody asked for it), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, a minimal `Permissions-Policy` and `Referrer-Policy: strict-origin-when-cross-origin`. A route's own stricter `no-referrer` (activation, OAuth callback) wins. Static assets are served by the platform without passing the Worker.
- `tests/e2e/security-headers.spec.ts` asserts them, and every e2e spec fails if the browser reports a CSP violation (`tests/e2e/test.ts`).

| What | Limit | Where |
| --- | --- | --- |
| Activation link, recovery code redemption | 5 per 10 minutes per IP (D28) | plugin `rateLimit`, `ACTIVATION_REDEEM_RATE_LIMIT`, `RECOVERY_REDEEM_RATE_LIMIT` |

Passkey sign-in and sending orders have no rate limit (D34); orders are bounded by the entry and position limits and by TradeStation's own limits. Covered by `tests/e2e/rate-limits.spec.ts`.

## Secrets

- Never in Git, logs, responses, bundles or URLs (the `guards` job scans every pull request's commits with a pinned gitleaks, and the `build` job greps the built client assets for secret names and token shapes with `scripts/check-client-bundle.ts`): TradeStation client secret and tokens, `BETTER_AUTH_SECRET`, `CREDENTIALS_KEY`. `client_id` appears only in the OAuth redirect. Activation tokens appear only in their activation link and in the one-time admin response that shows it; never in Git, logs, bundles or any other response.
- TradeStation secret and refresh token: AES-GCM via WebCrypto, random 12-byte nonce per value, `key_id` stored for rotation (the first 4 bytes of SHA-256 of the key, hex), the user id and field authenticated as additional data. `CREDENTIALS_KEY` is base64 of 32 random bytes. Encryption and decryption happen in the engine Worker. Rotation: the optional `CREDENTIALS_KEY_PREVIOUS` is used only to decrypt a row whose `key_id` names it; everything is encrypted with the current key, and a row on the previous key is re-encrypted at its next token refresh. A `key_id` that matches neither key fails closed (`KEY_UNKNOWN`, connection expired, reconnect required). Steps in [runbook.md](runbook.md#secrets).
- `audit_log` stores before/after of settings and roles, never credential values.

## Isolation

- A client reaches only their own DO (`idFromName(session.userId)`); account ids are checked against that client's accounts from TradeStation. The one exception is the e2e seeding route `/api/test/seed`, which addresses a DO by a body-supplied id; it exists only where `ENVIRONMENT` is `development` or `test` and answers 404 in production ([test-plan.md](test-plan.md)).
- Admin screens read client DOs; they never place or cancel orders.
